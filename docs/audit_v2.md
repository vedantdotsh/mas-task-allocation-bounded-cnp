# v2 results audit

Independent check of the surprising v2 results before the MEDES 2026 camera-ready. Date: 2026-11-12. Scope: `src/mas_sim/` (v2 path), `outputs/v2/`, `docs/results_v2.md`, `docs/model_notes.md`. Audit scripts were run from a scratch directory against the saved outputs and fresh re-simulations. No simulation parameter was changed.

**Summary.** The simulation contains no defects that change any number. All eight surprising results come from the model as specified. The live-LLM result comes from the model's own inaccuracy, not from the prompt or the parser. Three reporting problems were fixed: an E6 headline sentence that overstated the result, an LLM figure that hid one line and had ambiguous labels, and a ±5% margin verdict whose direction was unclear. A generated LLM error-distribution summary was also added. No simulation numbers moved, so E1–E6 were not rerun. The LLM experiment was replayed from cache only, and its aggregates are byte-identical. **Additional API spend: USD 0.00** (the journal is unchanged at USD 0.10217535 over 1,279 calls).

## Q1. Live LLM bids: real model inaccuracy, not a prompt or parser defect

**Verdict: the model is inaccurate. The experiment was left as it is.**

Prompt (`src/mas_sim/llm.py:22-46`): the system text states the exact formula. That is: wait until `max(now, committed_finish)`, then Euclidean distance from `queue_end_position` divided by speed, then workload divided by `max(proficiency, 0.05)`. The user message gives `now`, the task (location, workload, `required_skill`), and the agent's `skills`, `speed`, `queue_end_position`, `committed_finish` and queue. Everything needed is supplied, in consistent units. The comparator `bid()` = `Agent.estimate_cost` (`models.py:72`) uses the same position (the committed queue endpoint), the same queue term and the Euclidean, not squared, distance. When I recompute the formula **from the prompt text alone** for all 907 unique bid requests, I reproduce the run's error (mean |rel| 0.876 against the reported 0.83–0.93).

Parser (`llm.py:48`): it reads only the `bid` or `agent_id` key of a JSON object. All 1,278 cached responses are single-key objects (`{"bid": x}` or `{"agent_id": i}`). There are no prose or multi-number outputs, so it cannot take the wrong number.

Alternative interpretations were tested on non-zero bids (median |rel| for each). The intended formula gives 0.65. One-based skill index gives 0.72 (all bids). No queue term gives 0.68. Squared distance gives 0.97. Ignoring speed gives 0.69. Travel only gives 0.62. Distance only gives 0.60. Absolute finish time gives 0.90. None of them fits: under every hypothesis fewer than 9% of bids fall within 10%. So the model is not consistently answering some other question.

Error distribution, generated by the runner and pooled over all 1,113 valid logical bids (now in `llm_results.json` → `bid_error_distribution`):

| median abs | mean abs | within 10% | within 25% | median signed | overestimates | zero bids |
|---:|---:|---:|---:|---:|---:|---:|
| 0.685 | 0.872 | 3.9% | 9.9% | −0.56 | 24.4% | 10.1% |

The errors are mostly **underestimates**. 10% of bids are exactly 0, which is impossible because execution time is always positive, and a zero bid always wins. When the agent has a backlog, 23% of bids are smaller than the waiting time alone. The Spearman correlation between LLM and formula bids is 0.30. In centralized mode the model picks the true argmin 15.6% of the time, and the median rank of its pick is 4th.

What the experiment shows: `gpt-4o-mini` cannot do this square-root-and-division arithmetic reliably in a single-shot JSON answer at temperature 0. LLM-centralized routing over n agents degrades more than LLM bidding over k=3.

What it does **not** show:
- (a) Anything about LLMs that have a scratchpad, tools or a calculator. The prompt forbids explanation and caps output at 128 tokens.
- (b) That bidding as such is more robust to LLM error. In the CNP condition the k=3 shortlist is computed deterministically by the capability formula from the registry. The LLM only re-ranks the formula's top 3, while the centralized LLM chooses among all n. A random pick from the top 3 already agrees about 1/3 of the time, and the observed agreement is 0.41–0.46.
- (c) Sustained contention, because loads are 20–30 tasks.

I added (b) to the generated headline. Changing the prompt to allow reasoning would be a post-hoc design change, so it was not done.

Follow-up (not part of the original audit): a **worked** variant with step-by-step working, two zero-cost shortlist references and two more models were added alongside the one-shot run, which was neither changed nor rerun. See `docs/model_notes.md` and the generated live section of `docs/results_v2.md`.

## Q2. `formula_cnp` and `formula_centralized` are identical: legitimate

The two are separate `simulate()` calls (`llm.py:251`), with different ledgers: for example, 128 messages against 661 at n=24, seed 0. Re-simulating all 20 trials gives the same agent for **371 of 371 tasks**. The greedy winner is busy at decision time in only 16 tasks, and in each of them it is still inside the capability top-3. The capability shortlist ranks by travel plus execution, and the bid then adds backlog. With near-empty queues, greedy's argmin is the shortlist's first entry. Nothing is reused between conditions.

## Q3. Fewer invitations beat full information: real effect of a myopic rule

**Verdict: real.** Means over 30 trials at E3 defaults:

| policy | response | total travel | total execution | total busy | mean queue wait | same agent as greedy |
|---|---:|---:|---:|---:|---:|---:|
| greedy | 80.68 | 4555 | 2291 | 6847 | 46.4 | 100% |
| capability k=1 | 97.25 | 2981 | 2229 | 5210 | 71.2 | 19% |
| capability k=2 | 64.94 | 3561 | 2296 | 5856 | 35.6 | 23% |
| capability k=3 | 67.34 | 3913 | 2339 | 6252 | 36.1 | 26% |
| capability k=5 | 76.30 | 4319 | 2313 | 6632 | 43.1 | 36% |
| capability k=8 | 78.50 | 4483 | 2276 | 6759 | 44.7 | 70% |
| capability k=12 | 80.68 | 4555 | 2291 | 6847 | 46.4 | 100% |
| nearest k=2 | 69.77 | 3307 | 2716 | 6023 | 39.6 | 19% |

Travel rises with k in a straight line. Greedy minimises each task's own completion time, so it often sends a distant agent that happens to be idle. That spends 28% more travel than k=2 (+995 time units, 17% more total busy time), and the queues for later tasks get longer. At k=1 the rule cannot avoid backlog, which explains the U shape.

Consistency checks found no artefact:
- `service_start == dispatch + travel` holds for every assignment.
- In 30 seeds of CNP k=2, the winning wire bid equals the realised `finish − decision` to within 5e-7, which is the 6-decimal wire rounding.
- The capability shortlist ranks by registry state, and with s=1 the registry equals the true endpoint.

## Q4. `cached_central` equals greedy at 2 messages per task: legitimate

The update message (`v2.py:62`) carries `queue_end_position` and `committed_finish`. Skills and speed are static and arrive in the charged registration card. Together that is exactly what the bid formula needs. Each update is ledgered and tokenised.

Fresh state, no private load: 0 of 15,004 assignments differ from greedy (loads 200 and 300, 30 seeds each).

Independent replay: I rebuilt the registry **only from the serialized registration and status-update messages in the ledger** and recomputed every cached-central decision. That gives 13,874 awards across 10 seeds × {s=1,2,5,never} × {ρ=0,0.5,1} and **0 mismatches**. Under staleness or private load, the router therefore uses only what the directory would hold. Private jobs never update the registry; they show up only through the next managed update. The router diverges from greedy in 9,796 of those assignments, as expected.

## Q5. Random shortlist: fair

`v2.py:47` draws `rng.permutation(n)` per task from the protocol stream, so each task gets a fresh, uniform draw over all agents. Bids come from true local state (`v2.py:83`). Across 30 seeds, invitations per agent range from 2,438 to 2,536 (χ² p=0.99), and 790 of the 792 possible 5-subsets occur. No status updates are sent, so the rate is 2k+1. Random k=5 is worse because of distance (mean travel 33.5 against 21.6) and missed specialists. At k=12 it equals greedy, as it should.

## Q6. Message and token accounting: correct

Seed-0 ledgers, per task (`outputs/v2/audit/`):

| mechanism | per-task messages | stated identity |
|---|---|---|
| RR | 1 | 1 |
| nearest | 2 | 2 |
| cached central | 2 | 2 |
| CNP k=5 | 12 | 2k+2 |
| greedy | 25 | 2n+1 |

Each also has 12 registrations. SSI cfp/bid counts equal nB, with B awards. CBBA has 132 = n(n−1) consensus messages per round, plus 1 award per task.

All 62,540 seed-0 ledger messages were re-tokenised with `tiktoken` `o200k_base` on the stored serialized string: **0 mismatches**. The metadata records `tiktoken/o200k_base`, so the fallback estimate was not used. Polling response size grows exactly with the queue: 82.6, 140, 196, 252, … tokens for 0, 1, 2, 3, … items (+56 per item, `wire.py:52`). SSI vector bids list one `{task_id, cost}` per remaining task. CBBA messages carry the full bundle, claims and winner vectors (e.g. 238 tokens for a 7-task batch).

Minor note for the text: the CBBA winners vector serialised is the manager-level consensus snapshot, the same for every sender, rather than each agent's local belief. Its size is the same (one entry per task), so the costs are unaffected.
